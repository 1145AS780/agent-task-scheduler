# 版本号规范 — agent-task-scheduler v0.3.1.1：w17vbc

本文规定版本号怎么写、什么时候进位、发版前必须做什么。实现落点是文末的「版本号落点清单」，
改版本号时按那份清单逐个核对，别只改 SKILL.md 头部。

---

## 1. 格式

`vA.B.C.D：XXXXXX`

| 字段 | 含义 | 多久动一次 |
| --- | --- | --- |
| `A` | 世代位，从 0 起算，只有推倒重写才 +1（原 `-Rx` 前移） | 极慢，至今为 `0` |
| `B` | 安全与架构级重大变更（原 `A` 的职责） | 极慢，**攒够多次更新才动**（见 2.1） |
| `C` | 核心功能级里程碑，一整块新能力（原 `B` 的职责） | 慢，一个阶段一次 |
| `D` | 一批修补的汇总位（原 `C` 的职责） | 中，一批 bug/文档一起发 |
| `：XXXXXX` | 6 位字母或数字的构建码，**每次发版换一个**（原 `D` 的日常增量职责改由它承担） | 每次发版都换 |

数字部分只回答一个问题：**这个版本的兼容性与安全承诺是什么**。它一动，使用者才需要停下来重读
警告、重新评估；`：XXXXXX` 只回答「这是哪一次构建」。所以日常发版**数字不动、只换 6 位码**，
`0.3.1.1` 这个前缀可以跨很多次发布不变——这是「版本号不要跳太快」的机制解法，而不是靠少发版。

历史 tag 不必回改：旧 `v3.1.1` 在新口径下写作 `v0.3.1.1：<当时的码>`（原 `A.B.C` 整体右移一位、
前面补世代位 `0`），旧 tag 保持原样。本版数字沿用 GitHub 已发布的最新版 `3.1.1`，故为
`v0.3.1.1：w17vbc`。

> 冒号必须用**全角** `：`，不能换成半角 `:`——git 的 ref 名不允许半角冒号，半角写法根本打不出
> tag。已实测：`git check-ref-format "refs/tags/v0.3.1.1：w17vbc"` 通过，半角版本失败。
> GitHub 的 tag 页面链接会做百分号编码，不影响 `clone` / `fetch` / `checkout`。

## 2. 进位条件

**B（安全与架构位，原 `A`）—— 安全与底层机制大修（攒够了才进位）**

- 涉及安全边界、审核机制（看门狗、权限门、AST 预演）的大规模修复或加强
- 破坏性变更：旧状态文件不兼容，或既有任务升级后行为改变（例如被新边界拒跑）
- **累积门槛**：这一位不得为单次改动进位。要么先攒够至少 3 项 `C` 级变更，要么撞上一次路线图里
  事先写明的架构里程碑，才允许把它往前推一位。达不到门槛的安全修补走 `D`
- 纪律：进位时 `C`、`D` 强制清零；必须在版本历史与 Release Notes 顶部加安全警告；
  必须通知所有使用者重新 `seal --confirm`

**C（核心功能位，原 `B`）—— 核心功能里程碑**

- 加入**一整块**此前完全没有的能力（多语言插件、接入新下载器、新增 MCP 协议面等），
  且这一块需要使用者单独知道、单独评估
- 纪律：进位时 `D` 强制清零

**D（修补位，原 `C`）—— 一批修补**

- Bug 修复、文档更新、性能微调、不改 API 与行为的重构，**成批发布**时用这一位
- 单条的修补不动数字，只换 `：XXXXXX`

**A（世代位，原 `Rx`）—— 架构重置计数**

- 表示项目第 A 次「推倒重来」。触发条件：复杂度失控、模块耦合过高、技术债无法维护，
  由人主导（或采纳建议）做底层重写
- 独立于 `B.C.D` 递增，通常伴随一次 `B` 进位
- `0` 表示**至今零次重置**，这是计数起点，不是「第一代」。旧格式的 `R0` 就对应现在的 `A = 0`
- 只有真的推倒重写过，才写 `1`。把「开始使用这套规范」记成一次重置是错的——
  那会让世代位失去「重置过几次」这个唯一含义

**：XXXXXX（构建码，原 `D` 的日常增量）—— 日常增量**

- 同一数字下的追加：小范围功能补齐、协议文档补写、用例扩充、零散微调
- 6 位字母或数字，发版时随机生成或自选，**每次发版换一个新的，不复用旧值**
- 不改变兼容性与安全承诺，使用者不需要重读安全警告（但改了 `scripts/` 下 `.py` 仍须重封签，
  那是第 4 节第 4 条的机械约束，与版本位无关）
- **`C` 与构建码的分界线**：这块能力是否需要使用者停下来单独评估。需要 → `C`；不需要 → 只换码。
  拿不准时一律只换码——因为码的承诺更弱，写错位的代价更小

### 2.1 为什么数字必须「攒够了才动」

`B` 是数字里的第一位。它一动，使用者的第一反应是「要不要重读安全警告、要不要重封签」，
而这个反应的成本很高：一次 `B` 进位意味着全员重封签 + 重读破坏性变更说明。

如果每次发版都动数字，这个信号就被稀释成噪音——真正的安全升级反而混在里面看不出来。所以：

- **单次改动永不动数字**，哪怕它确实碰了权限代码；只换 `：XXXXXX`，等同类改动攒到 3 项，
  或者路线图里的架构里程碑真的到了，再一次性进位 `B`
- 版本号「跳得太快」的解药不是少改版本号，而是**让数字不动**：日常发版只换 6 位码，
  `0.3.1.1` 这个前缀可以跨很多次发布不变
- 反过来说，若一次改动既不新增能力、也不破坏兼容，就不该动 `C` 或 `D`——只换码
- 版本号只在**对外发布**（push + 打 tag）时才动。中间的过程提交不改版本串，
  否则同一个版本号会横跨多个提交，CHANGELOG 里就说不清「这个号到底发了什么」

## 4. 发布纪律

1. **全绿才能发**：`tests/lint.py` 与 `tests/selftest.py` 必须 100% 通过、退出码 0
2. **`B` 进位（安全/架构位）**：`CHANGELOG.md` 与 Release Notes 顶部加 `⚠️ 安全更新必读`；
   通知使用者重封签。只换 6 位码的版本反过来：不加 `⚠️` 安全警告段，只写变更摘要——
   但**重封签提示照旧要写**，因为第 4 条是机械约束、不是安全警告。警告段一旦泛滥，就没人读了
3. **世代进位要诚实**：`CHANGELOG.md` 必须用一段话写清「为什么重置、旧版哪里烂透了」，写给未来的自己
4. **重封签不是 `B` 进位专属**：`ats_guard.py` 的 `core_files()` 取的是 `scripts/` 下**全部 `.py`**，
   任何一个 `.py` 改动都会让 `ats_guard_manifest.json` 失配，`verify` 随即 `manifest_mismatch`。
   所以「改了 scripts 下任何脚本 → 必须 `seal --confirm` 重建基线」是机械约束，与版本位无关；
   `B` 进位的特殊之处只在于**必须主动通知使用者**，否则他们只会看到一条 `guard_check_failed`
5. **顺序**：所有代码与文档改完 → lint + selftest → `setup.bat` / `seal --confirm` 封签 → 提交 → 打 tag。
   封签必须最后做，封完再改 `.py` 等于把基线自己作废
6. **两处同步**：`CHANGELOG.md` 与 `SKILL.md` §15「版本历史」是同一份内容的两处落点，
   改版本时两边都要改；`CHANGELOG.md` 是给使用者看的发版文档，`SKILL.md` 是给 Agent 读的技能说明
7. **操作顺序看手册**：本节只讲「该做什么」，逐步命令、封签范围、落点实测与踩坑清单在
   [ATS-release-runbook.md](../ATS-release-runbook.md)，发版时按那份走一遍

## 5. 版本号落点清单（20 处）

改版本号时逐个核对，漏掉一处就会出现 `(v2.7)` 这种陈旧字样混在发版里（本项目 3.2.0-R0 之前
`ats.py` 就漏了 docstring 与 `--help` 两处，仍写着 v2.7）。

> 计数口径：`SKILL.md` 3 处 + `references/*.md` 10 份各 1 处 + `scripts/` 4 个文件共 7 处 = 20 处。
> 3.2.0-R0 时本表写的是「19 处」，漏数了本文件自己的标题行——`references/` 下实际有 10 份 `.md`
> （9 份主题文档 + 本文件）。这不是版本变更造成的增减，是原来的计数口径就少了一份。

| 文件 | 位置 | 形态 |
| --- | --- | --- |
| `SKILL.md` | 第 4 行 | `version: "0.3.1.1：w17vbc"` |
| `SKILL.md` | 第 7 行 | `# agent-task-scheduler v0.3.1.1：w17vbc` |
| `SKILL.md` | 版本历史表首行 | `\| 0.3.1.1：w17vbc \|` |
| `references/*.md`（10 份，含本文件） | 第 1 行 | `# … — agent-task-scheduler v0.3.1.1：w17vbc` |
| `scripts/ats.py` | docstring + `build_parser` 的 `description`（2 处） | `(v0.3.1.1：w17vbc)` |
| `scripts/ats_plan.py` | docstring + `description`（2 处） | `(v0.3.1.1：w17vbc)` |
| `scripts/ats_ui.py` | docstring + `VERSION` 常量（2 处） | `(v0.3.1.1：w17vbc)` / `VERSION = "0.3.1.1：w17vbc"` |
| `scripts/ats_torrent.py` | docstring（1 处） | `(v0.3.1.1：w17vbc)` |

只换 6 位码的落点与数字进位完全同一套清单，没有额外的落点——这也是加构建码的好处：
改动量不变，只是数字更不容易跳。换码时上面每一处都要换成**同一个新码**，不能只改一半。

> `ats_ui.py` 里还有一个**派生**常量 `HTTP_VERSION = VERSION.replace("：", "-")`，它是为了
> HTTP 响应头：`BaseHTTPRequestHandler` 用 latin-1 编码 `Server` 头，全角 `：` 编不进去，
> 会把每一条响应都打成 `UnicodeEncodeError`。所以**只改 `VERSION`、不要手改 `HTTP_VERSION`**，
> 它必须始终由 `VERSION` 派生；JSON 与页面里的版本号仍用全角 `：`（那些走 UTF-8，不受影响）。

`scripts/ats_mcp_http.py` 的 `(v1.0)` 与 `scripts/ats_mcp.py` 的 `SERVER_VERSION = "0.1.0"`
都是**模块自身**的版本号，不是项目版本，不随本项目进位（MCP 服务器有独立的协议与客户端兼容问题，
跟着项目版本一起跳只会让客户端误判）。

## 6. 历史判定（v4.0.0-R0 为什么是 A 而不是 B）

> 本节以下都是**旧格式口径**：旧 `A` = 现在的 `B`，旧 `B` = 现在的 `C`，旧 `C` = 现在的 `D`，
> 旧 `Rx` = 现在的世代位 `A`。历史 tag 不回改，判定理由照旧成立。

`v3.3.0-R0` 的 tag 已打到 `1b8443c` 并推到 origin，发出去的内容是 Task Visa / Plan Visa（82 条用例）。
本次待发版的是三块内容：**P0 执行目录边界**（`allow_dirs`）、**P1 控制台升级**（令牌闸门 / 白名单面板 /
`cwd` 下拉 / 窄屏适配）、**库级编排层** `api/ats_api.py`。

为什么进位到 A 而不是 B：第 2 节把「安全边界、审核机制的加强」明确列在 A 之下，而本次最重的一条
正是权限门本身的重写——任务 `cwd` 从「任意已存在的目录」收窄为「ATS root 内部 + `policy.allow_dirs`
每一项及其全部子孙」，边界要同时落在建阶段（`create` / `pack`）、执行前（`_start_task` / `_supervise`
两道二次校验）和 Plan 层的四个位置；`allow_dirs` 本身被列入 `RESTRICTED_POLICY_KEYS`，改它必须持人类
口令。控制台侧同理：绑非回环地址时从「谁都能连」变成「没有令牌文件就直接拒绝启动」，没有降级路径。

A 的第二条依据是行为不兼容：旧状态文件仍可读，但**既有任务的 `cwd` 若落在 root 之外，升级后会直接
`bad_cwd` / `cwd_outside_allowlist` 拒跑**。这属于「升级后行为改变」，必须按 A 的纪律在版本历史与
Release Notes 顶部加安全警告并通知使用者。

为什么不是 B：B 的定义是「加入此前完全没有的能力」。本次确实也新增了能力（白名单面板、`cwd` 下拉、
窄屏卡片、库级编排层），但把它们单独记成 B，会让只看 B 的人以为「不用看安全警告、不用重封签」，
而实际既有任务会因为边界收窄而拒跑。按第 2 节纪律，A 进位时 `B`、`C` 强制清零，故为 `4.0.0-R0`。

重封签：本次改了 `scripts/` 下三个 `.py`（`ats.py` / `ats_plan.py` / `ats_ui.py`），
按第 4 节第 4 条这是机械约束，与 A/B/C 无关，封完才能提交打 tag。

### 6.1 历史判定：v3.3.0-R0 为什么是 B 而不是 C

`v3.2.0-R0` 的 tag 已经在 2026-11-14 13:55:05 打到 `49d7476` 并推到 origin（tag 对象
`0899650`），发出去的内容是 extend 插件层 + torrent 公共 Tracker + 基础签证（75 条用例）。
那一版待发的是**此前完全没有的能力**：Task Visa / Plan Visa（作用域三选一、`approval_required`
自动放行、Plan 级联匹配、`unlimited` 只对 plan 开放）。按第 2 节，新增能力属 B、`C` 强制清零，
因此是 `v3.3.0-R0`，不是 `v3.2.1-R0`。

为什么不塞回已发布的 3.2.0-R0：tag 一旦推出去就是对外承诺。同一个版本号下改内容，会让
「拉 tag 的人」和「读 CHANGELOG 的人」拿到两套事实，且无法事后分辨。要改已发布内容只能新版本。

### 6.2 历史判定：v3.2.0-R0 为什么是 B 而不是 C

本次待发版内容包含一项**此前完全没有的能力**：`torrent` 自动注入 138 条公共 Tracker
（`DEFAULT_TRACKERS` + `ATS_TRACKERS` 覆盖开关 + `sanitize_trackers` 清洗 + 新事件字段
`trackers` / `tracker_source`）。按第 2 节，新增能力属 B，因此原计划的 `v3.1.2` 不合规，
应为 `v3.2.0-R0`。

同批还有一处**审核机制根路径修正**：`ats.py` 的 `ats_root()` 与 `ats_guard.py` 的 `resolve_root()`
默认根从 `<cwd>/.ats` 改为 `<ats 本体目录>/.ats`。它**不构成 A 进位**，依据：

- `ats.py` 调看门狗时始终显式传 `--root`（见 `_run_guard` 构造的 argv），执行器→看门狗这条路径
  从来没依赖过 cwd 默认值，所以它不是「权限门被绕过」的补丁
- cwd 默认值只影响**人类直接敲 `ats_guard.py`** 的场景：从别的目录 seal 会把清单写进错误根，
  人却以为修好了——修的是这个隐患，不是绕过
- 旧基线不会因此失效：在 `OCSKIS/` 下 seal 出来的清单本来就落在 `OCSKIS/.ats`，与新默认值同一路径；
  只有「从错误 cwd 封出来」的基线会换位置，而那些本来就不是有效基线

### 6.3 历史判定：v4.0.0-R0 为什么是 A 而不是 D

`v3.3.0-R0` 那次（4.0.0-R0 的内容）之所以必须进 A，是因为它**收窄了权限边界**：任务 `cwd`
从「任意已存在目录」收窄为「ATS root 内部 + `allow_dirs` 及其子孙」，且既有任务升级后会直接
`bad_cwd` / `cwd_outside_allowlist` 拒跑。这是「升级后行为改变」，属于第 2 节 A 的第一条。
当时没有 `D` 位，可选的低位只有 `C`，而 `C` 承载不了「旧任务会拒跑」这件事，所以只能进 A。

这条历史说明低位不是用来给安全变更降级的：**收窄边界永远进 `B` 或 `D`，构建码只装不改变承诺的增量**。

## 7. 本次判定（v0.3.1.1：w17vbc 为什么数字不动、只换码）

已发布的 `v4.0.0-R0`（tag 指向 `ae33a9a`，`origin/master` 基线）之后，`master` 上攒下了这些内容：

- 任务自动归档 + 容量闸：`failed` / `timeout` / `killed` 收尾后整目录搬进 `<root>/archive/<id>/`，
  运行目录不再堆已结束任务；读取侧由 `task_files_dir()` 统一「运行目录优先、archive 兜底」，
  `ATS_ARCHIVE_MAX_TASKS` / `ATS_ARCHIVE_MAX_BYTES` 控容量，配 `unarchive_task()` / `purge_archive()`
- 人类急停 `ats.py abort`：写 `<root>/abort.json`，除 `abort` / `approve` 外全部拒跑
- 维护态 `unpack` / `tryrun` / `repack`，实现拆到 `scripts/ats_maintenance.py`，
  `ats.py` 只保留延迟导入与函数转发
- 战情看板与回执：渲染拆到 `scripts/ats_telegraph.py`，写入侧（`receipt_path` / `append_receipt`）留在 `ats.py`
